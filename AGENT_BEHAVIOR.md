# Поведение агента и отдельная модель ответов

## Управление в Telegram

Откройте диалог → «Цель диалога» → «Прямота, настойчивость и границы».

- Цель остаётся отдельной инструкцией владельца.
- Прямота: обычный персональный стиль или более прямые формулировки.
- Настойчивость: умеренная или более последовательное продвижение к цели.
- Ограничения и полномочия: что можно делать и чего нельзя обещать.
- Условие остановки: когда дальнейшее продвижение к цели не требуется.
- Текущее состояние: ваши актуальные намерения, настроение, доступность.
  Обновляется вручную, действует до изменения или очистки; не превращается в память.

Без сохранённых настроек действуют обычный стиль и умеренная настойчивость.
Настройки не включают автоматическую отправку. Прямота и настойчивость не означают
давление после отказа. Старые примеры не дают разрешения повторить действие сейчас.

Кнопка «Ответ», «Указания для ответа» и `/reply` запрашивают три варианта текста.
Они больше не заменяются рекомендацией подождать. Даже для завершённого разговора
запрашиваются уместные короткие варианты. Если модель нарушила формат, бот покажет
ошибку, а не карточку паузы. Все варианты остаются предложениями для владельца.

Внутренний режим выбора `reply`, `wait` или `ask_owner` сохранён с явным параметром
`allow_decision=True`, но обычная генерация и тренировка его не включают.

## Обратная связь

Под ранее созданными решениями есть оценки: «Подходит», «Не та реакция», «Не мой стиль»,
«Выдуманы факты». Последняя оценка заменяет предыдущую. Сводка находится в
«Цель диалога» → «Оценки ответов». Это ручные оценки, не независимый тест качества.

Оценка «Подходит» не означает отправку и сама по себе не создаёт обучающий пример.
Для использования правки по-прежнему нужно связать реально отправленные сообщения
с черновиком и завершить разметку. Отрицательная оценка исключает эту генерацию
из подбираемых примеров правок; она не удаляет сообщения и исторические эпизоды.
Веса модели автоматически не обучаются.

## Тренировка на имеющейся истории

Откройте диалог → «Тренировка на истории» → «Следующий отрывок» →
«Получить варианты». Нажатие выбора отрывка не вызывает модель; генерация делает
один вызов настроенного генератора. В чат собеседнику ничего не отправляется.

Выбирается случайная ещё не использованная ситуация перед серией исходящих сообщений.
Модель видит до 24 предшествующих текстовых сообщений (до 14 000 символов), включая
полную последнюю входящую серию. Вся следующая серия ответов владельца скрыта.
Отрывки с удалёнными сообщениями, медиа или слишком длинным контекстом пропускаются.
Ранее написанные владельцем сообщения внутри контекста служат примерами стиля.

Текущая память, профили, глобальный стиль, цели, состояние, исправления и поиск
похожих эпизодов не используются: они могли быть построены по будущей переписке.
Это проверка продолжения по ограниченному контексту, а не проверка полного агента
со всей его памятью. Скрытый ответ не передаётся модели даже после его открытия.

Каждый из трёх вариантов оценивается отдельно. «Показать мой ответ» открывает
реальное продолжение для сравнения. Последняя оценка заменяет предыдущую;
оценки, поставленные после раскрытия ответа, помечаются отдельно. Сохранённый
результат повторно не генерируется при открытии или повторном нажатии кнопки.
При ошибке запроса можно явно повторить генерацию в том же отрывке.

Упражнения сохраняются в `reply_practice/<id>.json` внутри workspace диалога:
ID исходных сообщений, контрольная сумма источника, точный запрос, модель,
варианты, оценки и момент раскрытия ответа. История и рабочий журнал ответов
не переписываются. После удаления или изменения источника отрывок блокируется.
Сами сохранённые файлы упражнения при этом не удаляются автоматически.

Это сбор материала для дальнейшего обучения и проверки. Оценки пока не меняют
веса модели и не подмешиваются в рабочие ответы. Массовое обучение не запускается.

## Подготовка настоящего дообучения

В тренировке есть «Данные для дообучения» → «Подготовить набор».
Это локальная операция без API. Она создаёт новую версию в
`learning/datasets/<id>/` внутри workspace текущего диалога:

- `train.jsonl` — контекст и реальный ответ для обучения;
- `valid.jsonl` — отдельные поздние ситуации для проверки;
- `sources.json` — исходные ID и контрольные суммы;
- `manifest.json` — владелец, диалог, граница разделения, размеры и контрольные суммы файлов.

Последние 20% сообщений отводятся под проверку. Окна, пересекающие границу,
отбрасываются; между выборками нет общих исходных сообщений. Все исходные сообщения
упражнений ручной тренировки исключаются из обучающей части. Если после исключений
данных мало, подготовка останавливается, а не использует одни примеры дважды.
По умолчанию сохраняется не более 2000 примеров в каждой части. Старые версии
и исходная переписка не перезаписываются. Это техническое разделение данных,
а не гарантия разнообразия, качества или отсутствия похожих формулировок.

Скрипт `python -m scripts.train_reply_adapter --account ACCOUNT_ID --dialog DIALOG_ID
--dataset DATASET_ID` проверяет набор без загрузки модели. Используется окружение
проекта с его обычной конфигурацией. При изменённых/удалённых источниках или появлении
пересечения с новыми упражнениями требуется подготовить новую версию набора.

Для явного запуска добавляются `--train --model-path /путь/к/готовой/модели
--steps 100 --max-length 2048`. Обучающие зависимости перечислены отдельно в
`requirements-training.txt`: рабочему Telegram-боту они не нужны. Модель должна
быть уже скачана, иметь шаблон чата и поддерживаться Transformers/PEFT.
Скрипт не скачивает модель, не исполняет её remote code и не публикует данные.

LoRA обучается на конечном ответе владельца (`completion_only_loss`), а не на
репликах собеседника и не на всех промежуточных ответах в контексте. Примеры,
не помещающиеся в токенный предел, целиком пропускаются. Веса сохраняются в
`learning/adapters/<id>/adapter`; `run.json` фиксирует набор, базовую модель,
параметры, статус и validation loss до/после. Промежуточные checkpoints сохраняются;
автоматическое возобновление не реализовано. Набор и адаптер принадлежат одному
диалогу: не подключайте такой адаптер глобально ко всем чатам.

Снижение validation loss не доказывает, что ответы стали похожи на ваши.
Адаптер имеет статус `trained_unapproved` и не активируется автоматически.
Этот этап обучает один ответ по контексту; качество работы с рабочим промптом,
целями и форматом трёх вариантов ещё нужно проверять отдельно перед подключением.
Полное обучение на реальном оборудовании не запускалось: совместимость выбранной
модели, зависимости, доступная память и скорость пока не проверены.

Формат и интерфейс: [TRL SFTTrainer 0.29.0](https://huggingface.co/docs/trl/v0.29.0/en/sft_trainer).

## Хранение

В активном workspace при первом сохранении создаётся `dialog_behavior.json`
с account_id и dialog_id. Чужой или повреждённый файл блокирует использование
настроек; автоматического восстановления из другого диалога нет.

При следующем открытии журнала добавляются таблицы `generation_evidence` и
`generation_reviews` в существующий `reply_journal.sqlite3`. Прежние строки и
таблицы сохраняются. Новые генерации из Telegram записывают полный входной запрос,
системную инструкцию, модель, ID текущего контекста и решение. Старые записи
задним числом не дополняются. Снимки могут содержать личную переписку и увеличивают
размер журнала; они не экспортируются и автоматически не используются для обучения.

`ai_request_preview.txt` теперь содержит читаемый JSON со снимком запроса,
включая системную инструкцию; это тот же запрос, который отправляется модели.
API-ключи туда не записываются. Терминальный интерфейс показывает решения и пишет
этот preview, но разметка и журнал генераций доступны через Telegram.

## Модель ответов

По умолчанию используется прежний OpenAI Responses API и `OPENAI_MODEL`.
Переменная `REPLY_MODEL` может отдельно переопределить модель генерации ответов.

Для уже запущенного сервера, совместимого с Chat Completions API:

```dotenv
REPLY_PROVIDER=compatible
REPLY_BASE_URL=http://127.0.0.1:8000/v1
REPLY_MODEL=your-served-model
REPLY_API_KEY=
```

Адрес и имя модели должны соответствовать вашему серверу. Пустой ключ заменяется
служебным значением `local-no-key`; для сервера с авторизацией задайте отдельный ключ.
Ключ OpenAI никогда не подставляется в запрос к этому серверу. После изменения
настроек нужен перезапуск. Если сервер недоступен или ответ некорректен, генерация
завершается ошибкой без автоматического переключения на другого провайдера.

Сервер должен поддерживать `system`/`user` messages, `max_tokens` и возвращать текст
в `choices[0].message.content`. JSON решения проверяется локально. Совместимость
конкретного сервера и модели нужно проверить отдельно; модель не скачивается,
не запускается и не дообучается этим изменением.
Формат запроса: [официальная документация Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

**Это замена только генератора ответов.** Анализ истории, поиск и эмбеддинги всё ещё
используют прежнюю конфигурацию OpenAI и требуют `OPENAI_API_KEY`. Даже при локальном
генераторе поиск контекста может отправлять данные в OpenAI. Полностью автономный
локальный режим этим изменением не реализован.

## Проверки

```bash
API_ID=1 OPENAI_API_KEY=offline-test PYTHONDONTWRITEBYTECODE=1 venv/bin/python -m unittest discover -s tests -q
```

Тесты используют временные workspace и подменённые API. Проверяются изоляция,
атомарное сохранение, устаревшие кнопки, контракт решений, выбор провайдера,
связь решения с журналом и отсутствие отправки собеседнику.
